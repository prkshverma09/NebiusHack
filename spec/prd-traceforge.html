TraceForge: every call trains its replacement — a specialist model for every task your agents repeat

A working clone of mubit.ai's core loop built entirely on Nebius Token Factory. An OpenAI-compatible gateway fingerprints every agent call into a task, captures verified frontier-model traces as training data, distills a small open "Bonsai" model per task via LoRA, lets it prove itself in shadow mode on live traffic, and only then promotes it — all verified on two held-out benchmarks. One gateway in; a fleet of promoted specialists out.

01Summary and the one-sentence pitch

"Point any agent at our proxy. It earns each task a specialist model — trained on the frontier model's own verified answers — and promotes that specialist only after it beats its shadow-mode trial. Two tasks, two promoted Bonsai models, ~30× cheaper, live on stage."

This compresses Mubit's entire product thesis into a one-day, benchmark-verified build: capture → fingerprint → verify → distill → shadow → promote. Nothing in the demo is simulated — every score is a deterministic grade and every call a real API request.

Deliverable

Working API + dashboard: gateway, task fingerprinting, per-task datasets, two LoRA distills, shadow/promotion router, eval harness. Every number real.

Proof

Two held-out benchmarks, three model bars each: base student, promoted Bonsai, frontier teacher — plus a live shadow win-rate ticker.

Fit

Implements Nebius's own Data Lab thesis — "your best dataset is already in your logs" — end-to-end on their post-training surface. The demo is a Token Factory showcase.

Budget

Est. $20–45 of $150 — two fine-tune jobs, teacher traces, evals, and demo-day inference with headroom.

02Problem and users

The problem

  • Agent builders pay frontier prices forever — every repeated task re-pays the "intelligence tax" even though the task stopped changing months ago.
  • Different tasks need different specialists. A router, an extractor and a SQL writer shouldn't share one generic expensive brain — but nobody wants to babysit three fine-tunes.
  • The raw material to fix it — the agent's own successful traces — is thrown away or locked in observability dashboards that end at charts.
  • Going from traces to a trusted replacement needs capture, grading, datasets, training, deployment and a safe way to swap traffic — days of plumbing before a single trained token.

Who it's for

  • Agent developers running repeated task shapes (extraction, routing, tool calls, NL→SQL) who want frontier quality at open-model prices — without hand-managing adapters.
  • Hackathon judges — the persona that matters on the day. They need to watch a specialist earn promotion in under 3 minutes, with real numbers.
  • Us — a reusable asset: the same loop works for ForgeAI's invoice domain and any future agent.

The science has a name — and judges should hear it. Verified-trace distillation is rejection-sampling fine-tuning (STaR/RFT lineage): keep only trajectories that pass an external checker, train on them, iterate. FireAct showed GPT-4 trajectories lift a 7B model +77% on HotpotQA; xLAM's 1B fine-tune beats GPT-4-class models on BFCL. TraceForge productizes that recipe behind one API.

04System architecture

05The distillation loop, per task

  1. Fingerprint. Every proxied call gets task_id = hash(system + tools + response_format). The two demo agents emit exactly two task groups — "a model for every task" is automatic, not configured.
  2. Capture. Benchmark runners send train-split items through the gateway; the teacher answers; each trace row stores messages, tools, tool_calls, usage, latency, computed cost, fingerprint.
  3. Grade. Deterministic per-task checkers: exec-match for SQL (run the generated query on the real sqlite DB, compare rows), AST match for tool calls. Verdict + detail persisted. No LLM judge for the headline number.
  4. Build. Verified traces per fingerprint → deduped, balanced train/val JSONL; also pushed to Nebius Data Lab so judges see the dataset in Nebius's own console.
  5. Distill. Two LoRA jobs in parallel (Llama-3.1-8B primary; 3.2-1B if time). Checkpoints deployed as bonsai-sql-v1, bonsai-fc-v1.
  6. Shadow. Promoted-candidate runs alongside the teacher on fresh traffic: both answer, the grader scores both, the win-rate ticker fills. This is the trust-building phase Mubit calls "evaluate changes before rollout".
  7. Promote. Gate = shadow win-rate ≥ threshold + held-out eval ≥ teacher − margin. On pass, route=auto serves that fingerprint from Bonsai — flip shown live.
  8. Iterate (stretch). Promoted-model failures on new traffic are harvested, teacher-corrected, and submitted as a v2 job — the learning staircase on the final chart.

06Model lifecycle: candidate → shadow → promoted

The feature that turns a fine-tune into a product: nobody trusts a model that just appeared. TraceForge makes each Bonsai earn its traffic.

07Component specifications

7.1 Trace gateway proxy + fingerprint

OpenAI-compatible /v1/chat/completions. Forwards losslessly to the upstream model the router selects, records request/response verbatim (tools, tool_calls), computes cost per call, assigns session + task fingerprint. Fail-open on logging errors.

7.2 Trace store + cost ledger sqlite

Tables: traces, grades, tasks, datasets, finetune_jobs, models (lifecycle state), eval_runs, eval_items, cost_ledger (per-call teacher-vs-bonsai spend powering the dashboard ticker).

7.3 Graders deterministic

SQLExecGrader — executes generated SQL on the task's sqlite DB, compares result sets (Spider-style). BFCLGrader — AST match vs ground-truth call. FailureTaxonomy — classifies misses (wrong table / wrong args / hallucinated name) for the dashboard's "why distillation works" panel.

7.4 Dataset builders per task

Per fingerprint: filter grade=correct, dedupe, split train/val, emit Nebius JSONL; report token count → cost preview before submit. One extra call pushes the dataset to Data Lab.

7.5 Distill orchestrator nebius

files.create → fine_tuning.jobs.create → poll → POST /v0/models per task; jobs run in parallel. Stores job id, trained_tokens, checkpoint, deployed name. Model row enters lifecycle as candidate.

7.6 Shadow router + promotion gate the differentiator

Routes by fingerprint: teacher | bonsai | auto. In shadow, the candidate answers in parallel (async, graded, never returned to the caller). Gate: shadow win-rate ≥ teacher − margin over N calls and held-out eval pass → promoted. One flag rolls back.

7.7 Eval harness proof

Concurrent runner over held-out items × model list; per-item verdicts persisted; emits the score table, failure taxonomy, and the Pareto (accuracy vs $/M) chart data.

7.8 Dashboard demo surface

Single page: live trace feed grouped by fingerprint, per-task lifecycle state with promotion gate progress, $ counter (teacher spend · bonsai spend · saved), three-bar score charts, failure-replay buttons, and the Pareto frontier.

09Benchmark & demo data plan — two tasks, two specialists

Two benchmarks chosen for complementary wow: Spider (text-to-SQL) is the judge-interactive, business-flavoured demo; BFCL (function calling) is the on-theme agent benchmark with public leaderboard precedent. Both grade deterministically. Together they prove the gateway's fingerprinting really does produce "a model for every task" — not a hardcoded pipeline.

TaskDatasetGradingDemo momentPrecedent
task:nl2sql Spider slice (~800–1,200 train / ~300 test, small schemas; bundled sqlite DBs) Execution match — run generated SQL, compare result sets Judges type a question live; Bonsai emits SQL that executes on the real DB Fine-tuning documented to lift models ~61% → 82%+ exec accuracy
task:toolcalls BFCL v3/v4 AST slice (~800–1,500 items: simple, multiple, parallel, irrelevance) AST match vs ground-truth function call Failure-replay: base student's wrong call → Bonsai's correct AST, side-by-side xLAM-1B / Hammer-3B fine-tunes beat GPT-4-class on public leaderboard

Why two tasks is the winning move. A single benchmark proves distillation works. Two specialists emerging from one gateway — with separate fingerprints, datasets, models and promotion gates — proves the product works. That's the difference between a fine-tuning tutorial and a Mubit clone.

Rejected alternatives (kept honest). GSM8K — works but judges have seen it forever. HotpotQA/FireAct — strong precedent, weaker demo visuals; kept as stretch. SROIE/CORD extraction — our ForgeAI domain; swap-in if either primary collapses on the day. τ-bench/SWE-bench — needs env infra, out for one day.

Contamination hygiene. Teacher traces are generated on the train split only; test items never touch the teacher until eval. Judges get the split logic in one sentence — it preempts the "did the small model just memorize?" question.

12Functional & non-functional requirements

Functional

  • Must Lossless /v1/chat/completions proxy — identical response bytes to calling upstream directly.
  • Must Task fingerprinting; traces persist with tools/tool_calls verbatim, usage, latency, cost.
  • Must Two deterministic graders (SQL exec-match, BFCL AST); verdicts + failure taxonomy persisted.
  • Must Per-task dataset builder → valid Nebius JSONL + train/val split.
  • Must Orchestrate upload → job → deploy per task; parallel jobs.
  • Must Shadow mode: candidate answers live calls in parallel, graded, never user-visible.
  • Must Promotion gate + one-flag rollback; lifecycle states visible.
  • Must Eval harness: 3-model score table per task on held-out items.
  • Must Dashboard: trace feed, promotion board, $ counter, failure replay.
  • Should Data Lab dataset push; judge-input endpoint scoped to demo tasks.
  • Should Pareto chart; streaming proxying.
  • Could v2 staircase retrain; 1B student; custom speculator; batch-inference evals.

Non-functional

  • Must Nothing faked — every score is a deterministic grade on a real API response. No mock mode; doubles live in tests/.
  • Must Gateway overhead <50 ms; shadow calls async off the hot path.
  • Must Secrets via env (NEBIUS_API_KEY); never logged or rendered.
  • Must Held-out split untouched by teacher before eval (contamination firewall).
  • Should Single uvicorn + one SQLite file; make demo re-runs the whole loop.
  • Should Judge-input sandboxed: only the two demo tasks, rate-limited.
  • Could Recorded-replay fallback (clearly labelled, never scored) if the venue network dies.

143-minute demo script

  1. The claim (15s). "Your agent's most expensive line item is a model that answers the same five tasks forever. We built a Mubit-style clone on Nebius: every call trains its own replacement — and the replacement has to earn the job."
  2. Judge input (30s). "Somebody ask this database a question." Their question flows through the gateway → teacher answers → the trace appears live in the feed, fingerprinted task:nl2sql, graded.
  3. The loop (35s). Architecture walk: two task groups → per-task verified datasets → two LoRA jobs on Token Factory (show real trained_tokens) → deployed as bonsai-sql-v1, bonsai-fc-v1. Flash the same datasets sitting in Data Lab — "your logs are your dataset."
  4. Shadow trial (40s). Promotion board: live win-rate ticker for each candidate; explain the gate. Then the flip — route=auto — and rerun the judge's earlier question on the promoted endpoint. SQL executes on the real DB. Same answer.
  5. The receipts (45s). Score tables per task (base 8B → bonsai → teacher), failure replay on the tool-call task (wrong call → correct AST), Pareto chart with Bonsai on the frontier, and the $ counter: teacher spend vs saved, still ticking.
  6. The close (15s). "One line to adopt: base_url. The specialists it builds are yours — open weights on Nebius. All of this ran for under forty dollars."

Risk-managed liveness. Judge input is optional and scoped — if the room's network or nerve fails, pre-staged "judge questions" replay the same path. The staircase (v2 retrain) is shown only if the second job landed; otherwise it's the roadmap slide. The demo never depends on the stretch goals.
